# 持续服务助手：能力包、角色、流程和可恢复状态

新对话是使用入口之一，不是服务能力本身。交付可迁移的助手包，在支持的宿主中可以配置为专属项目/Agent，也可由用户在新对话中载入。不能凭创建对话声称具备知识、记忆或后台执行能力。

## 一个可独立使用的包

按 [能力交付规则](capability-delivery.md) 包含 `SKILL.md`、`knowledge/` 与 `trial.md`，另外生成：

| 文件 | 要解决的问题 |
|---|---|
| `ROLE.md` | 我提供什么服务，使用什么依据，如何与用户协作，哪些问题超出范围 |
| `SERVICE.md` | 初次了解 → 诊断/判断 → 交付 → 实际反馈 → 修订的领域适配流程 |
| `START.md` | 如何将整个包交给当前平台、启动文本、检查文件是否真的可读、指定私人工作目录 |
| `workspace-template/profile.md` | 空白用户背景与目标结构，区分事实、假设、未知、来源及更新时间 |
| `workspace-template/state.md` | 空白当前问题、决定及理由、待办/负责人/状态、未解决事项、下次从何处继续 |
| `workspace-template/history.md` | 空白服务记录结构：日期、输入、产出、实际反馈、修订原因及关联文件 |

`SKILL.md` 是服务入口，明确读取 ROLE、SERVICE，再根据当前任务从知识库选取资料。无需单独安装思考型或表达型包；需要的分析与表达流程已包含。不要把“去调用一个未交付 Skill”当作服务能力。

## 角色定义

根据用户希望获得的服务和原材料支持范围，写成“基于某体系的某类辅助服务”。记录专业视角、证据标准、决策偏好、沟通方式和任务边界。有依据才能归纳这些特点，不虚构完整人格、私人情绪或人生经历。

助手不是原作者本人，不声称得到其授权或继承职业资格。法律、医学等材料也可使用，但服务流程必须落实 [领域边界](domain-boundaries.md) 中的事实核验、时间/地区/人群要求；需要外部验证而没有工具时明确受限，不能把讲述者经验直接当现行规则。

## 持续服务流程

- 首次只收集本次服务必要的用户目标、背景与约束；资料已有就读取，不反复问同样的问题。
- 判断时把用户事实、知识依据和新推导分开；交付具体到本次问题，必要时提出待验证方案。
- 每次结束形成可恢复状态：本次做了什么、依据、用户是否采纳、实际结果还是预测、待办与下次切入点。没有真实反馈写“待反馈”。
- 新对话先读取角色、流程和实际私人工作目录中的 profile/state；按需要读 history 相关段落、知识卡和证据，说明当前恢复到哪个状态。有缺档先报告，不假称记得上一段对话。
- 用户反馈与知识冲突时回查依据、记录修改理由；个案反馈不自动改成讲述者的普遍观点。原始知识快照与用户状态分别维护。

## 启动与跨平台交付

START 中根据交付包实际名称和文件写出可复制文本，例如让用户指定包和私人工作目录，要求助手“先检查并读取 SKILL.md、ROLE.md、SERVICE.md，再读取已有状态；状态为空时补问当前目标，按任务取用 knowledge”。生成成品时提供实际相对目录示例，避免只交抽象说明。

首次使用，在用户指定、已授权可写的私人工作目录建立状态文件，使用模板副本，不把个人记录写回可分发包。存在旧记录时读取并继续，不能覆盖为空白。没有持久文件工具时输出本次状态块，告诉用户下次必须一起提供；不能承诺自动记忆。

只有用户要求新建对话/项目且当前工具支持时，才执行创建并配置文件访问，随后检查新环境能否读取。否则交付 START，状态标为“包已交付，尚未在宿主启动”。仅传递本地路径并不等于远程/云端能够读取。

后台提醒、定时跟进、发消息、对外操作与跨平台同步不是本包自带能力；用户确有要求时再依据宿主能力和权限配置。持续服务默认指用户再次调用时能衔接。

## 验收

除通用知识及包检查外，用一个任务验证初次问询、判断与交付，再将完成后的状态交给独立的新会话/执行上下文检查恢复情况（仅在对应创建操作获授权时）。未执行新上下文验证就写“恢复协议已检查，跨会话恢复未实测”。不能以 ROLE.md 存在替代服务验证。
